# Testing

Shallot-specific testing patterns.

**A gate verifies and never writes; `bun run format` is the only writer.** `bun check` reports and exits without touching the tree, so the state you read before it is the state you commit.

## GPU testing

Readback layout arithmetic comes from the owning exported column constants, never a duplicated stride or offset; bitcast identifiers are asserted through the matching integer view before any numeric interpretation.

Two surfaces, one source of truth each, no overlap. The boundary is one question: does the assertion's truth depend on the real GPU?

- **Logic — `bun test`.** Hardware-invariant correctness: schema-derived layout/stride/offset, resolved WGSL structure, bind-group-layout construction, packing/encoding, ECS, audio DSP, physics math, and CPU execution of pure TGSL kernels against deterministic references. A CPU-callable kernel is the logic-truth surface for the same authored function the GPU pipeline resolves; it proves math and addressing, not device execution. Keep any hot plain-JS packer mirror bit-identical with a differential sweep. No device needed. The root `bunfig.toml` preloads bun-webgpu globals plus the TypeGPU transform so imports and TGSL CPU arms work — an import shim, not a device under test. Run `bun test` from the repo root; from `packages/shallot` the preload paths don't resolve and modules die at import with `GPUShaderStage is not defined`. In WSL the only adapter is software (Mesa llvmpipe; dzn, the real-GPU path, is non-conformant and Dawn rejects it), so `bun test` is not a real-GPU signal. **A default-suite `bun test` file's verdict must not depend on the device *executing*** — readback values, dispatch results, pipeline execution — the lavapipe adapter is slow, flaky, and feature-incomplete (no usable subgroups/timestamp, `build()` can time out), so a verdict the device's execution decides is unreliable, not a signal ("GPU behavior lives in Playwright" below). Binding the preloaded adapter is not itself the banned act and cannot be: engine `build()` calls `requestGPU` unconditionally, so default-suite files that bootstrap through it bind the adapter everywhere — the execution verdict is the banned thing. Two sanctioned departures from the property: the slab reset/in-flight-stager lifecycle race (`src/standard/slab/slab.test.ts`, default suite — its verdict rests on real `mapAsync` staging repooling, the race the gym can't reach), and, by path and never by default, a `.tier.ts` that runs its verdict through the preloaded adapter for a measured build/lifecycle probe — the physics `tests/avbd/headless.tier.ts` and the conformance roster's Physics/Character/Player arms at `capacity: 8192` (avbd.md "software-adapter tier" holds the derivation). The tier stays a de-risking probe, never a correctness oracle, and never part of the default suite. The default suite's candidates are found by grepping its `*.test.ts` for the readback seams (`probeBuffer`, `mapAsync`, `.read()`) and adjudicating each hit against the property — never by a hand count, and never restated as one ("the one arm that…" is a universal over a hand-counted population, and such a population drifts the moment a file is added). Don't assert hardware-variable behavior (subgroup width, f16, raster) here at all.
- **GPU behavior — `bun bench`.** The single source of truth for anything whose truth depends on the real device: pipeline/shader compile, bind-group validity, compute-kernel output (Mirror readback), raster, graphics-stage storage, hardware-variable behavior (subgroup width, f16), perf, visual. Playwright drives the real GPU via the gym example. Assert each GPU behavior exactly once, here — even where `bun-webgpu` binds a real adapter (native Mac / Windows / hardware Linux), so the suite reads identically everywhere instead of depending on the contributor's GPU. It's the **targeted** tier: run one atom at a time (`bun bench --scenario X`) after its domain changes. Running more than one is a *selection*, never a run-all — which scenarios and how they execute is "Selecting and sweeping bench scenarios" below.

**Dawn rejects `createShaderModule` when an `enable` directive names an extension the device didn't enable** — so a green bench run on a device that never *requested* a feature is a real oracle for "the engine doesn't need it", not a proxy (the `shader-f16` floor removal was proven this way; a compile failure is a hard nonzero exit).

Nothing is skipped and nothing false-fails, because no test lives in a tier that can't run it. Raster needs graphics-stage storage the software adapter lacks, so it's bench-only by construction — never a skipped unit test. A "false failure" is a tier violation: a real-GPU assertion that leaked into `bun test`. Move it to bench; don't skip it.

### Selecting and sweeping bench scenarios

Which scenarios gate a changed file is a lookup, not a guess. `SCENARIO_GATES` (`examples/gym/src/scenarios/timeouts.ts`) carries `{ timeoutMs?, isolate?, covers[] }` per registered scenario — plain data with no imports, so a driver resolves a path to scenario names node-side without booting a page. `bun bench --list` prints the real roster from registration (names are registration slugs, not filenames); `bun bench --for <paths…>` resolves changed paths through the `covers` globs; `bun bench --sweep [--for …]` runs the selection.

- **Batch is for correctness verdicts; perf rows get their own process.** `--sweep` drives `shallot verify`'s batch mode (`--run`, repeatable): one server boot, one browser launch, a fresh context + page per run, one verdict each. `one page load = one verdict` is preserved exactly. A scenario whose asserts carry a perf threshold declares `isolate: true` and the sweep spawns it alone — thresholds measured under back-to-back sweep contention are not trustworthy (`stress` failed mid-sweep on its bandwidth/submission rows and passed standalone at two commits). `render` and `character` are isolated for the same reason.
- **A roster-wide gate is re-run only by a diff that can move the roster.** `--sweep` gates cross-scenario quantities (the budget goldens); a diff inside one scenario's asserts cannot move another row's pipeline count or byte total, so the gate it owes is `--scenario X`, repeated as many times as the property needs. The trap is a spec Validation line naming `--sweep`: once written it reads as *this unit's* gate, and later stages re-pay 350 s for a criterion that closed several stages ago. Re-run the gate whose quantity the diff can actually change, and say which one you skipped and why. Measured on a one-scenario check deletion that reached for the full sweep out of habit.
- **An all-at-once batch failure is a known flake, not a regression — retry before diagnosing.** Under the WSL bridge, a full sweep occasionally returns `no result (verify crashed before reporting)` for *every* batch scenario at once, isolate rows unaffected, nothing on stderr, self-resolving on retry (2 of 4 attempts, 2026-08-04). Calling `verifyBatch` directly with the identical list and params succeeded 3/3 including under `quiet`, so it is not a `sweep()` logic bug — it is specific to the full CLI path under the bridge. All-or-nothing is the tell: a real regression hits some scenarios, this hits all of them.
- **`--memory` is opt-in on the sweep path**, always on for a single run. It costs ~1.2 s per run, gates nothing, and prints `⚠ LEAK` on a passing run — a warning that fires green trains readers to ignore warnings.
- **The map selects within the GPU tier only.** `--for` on a `standard/tumble/**` path matches nothing and says so, pointing at `tumble.md`'s gates; the tumble and AVBD-oracle tiers keep their own selection rules (`.oracle.ts` below). A path outside the GPU population gets the same treatment, never an empty roster that reads like "nothing gates this."
- **The map's own gate runs in the gym tier.** `examples/gym/src/scenarios/coverage.ts` asserts coverage both directions — every `covers` glob resolves, every registered scenario has an entry, covered ∪ exempt equals the GPU-side module population, covered ∩ exempt is empty, every exemption names a reason. It lives outside the default gate's explicit paths (`bun run test` doesn't include `examples/gym/src`; it needs the scenario roster), so **`bun run test` does not run it**: after adding a GPU-side module, a scenario, or a `covers` entry, run `bun test ./examples/gym/src`.
- **An exemption's reason claims the load-bearing property, never a structural shape.** "Barrel re-export, no logic of its own" was false twice in three uses, on files carrying hundreds of lines of plugin code. Say the property that actually exempts it (CPU-only, no GPU/WGSL surface) — a structural claim is cheap to assert falsely and expensive for a reader to re-verify. Shadowing is caught mechanically; a true exemption with a false reason is not.
- **A text check over a module-flat resolve is scoped to the wrong unit.** `tgpu.resolve` concatenates a whole call graph's bodies into one string; a check correlating two *named* things across that string (`pointerDiscipline` matching `(&name)` against an unrelated function's `let name =`) can collide at corpus scale though a self-contained lexical pattern can't — scope it to the emitted function body, not the module. A corpus-wide false positive trains its reader to ignore the gate faster than a declared exemption does.
- **A corpus-wide exemption keys the resolved subject, not the call graph's shape.** `tgpu.resolve` inlines every transitive caller, so one leaf's violation reds every kernel that calls it — triage the leaf first and read a multi-kernel red as one candidate defect, not several rows to write. A caller's own legitimate exemption still needs its own row keyed on the resolved kernel, not the call seam: shadowing a callee's row would silently exempt whatever else that caller does. Measured on the TGSL discipline checks: 101 kernels, four exemption rows, one leaf fix clearing six reds.
- **A completeness registry needs a "neither" arm, or the third case lies.** Forcing every subject into has-it/can't-have-it makes "doesn't apply yet" masquerade as one of the other two. Declare the gap, and freeze its occupants **by name** — a count golden passes a swap (one gap closed while a different subject takes the cheap arm). The TGSL differential registry: 61 named tests, 10 can't-have mechanisms, 30 named gaps. **One row per subject, never one per arm** — a per-arm registry lets a row be deleted with nothing red, since presence-of-some-row is all it can assert, while one row per subject makes deletion a red and turns the registry into a burn-down. **The rows earn the registry only where they carry a machine-checkable claim**: a walked population whose rows hold prose alone is a discipline ledger, not a gate, and every classification defect in the CLI registry's own history was caught by a reader rather than by its check.
- **A "references the symbol" check is satisfiable by a mention, and call syntax alone doesn't close it.** An unused import, or a name inside a comment, passes a bare `\bsymbol\b` grep with nothing actually called. Requiring call syntax (`callsSymbol`) narrows that but doesn't settle it: a `toContain("fn symbol(")` string literal, a commented-out call, and a same-named local `function symbol(` definition all match while calling nothing real. It takes a second independent check — `importsSymbol`, a real import binding for the name found in call position, run uniformly over every row rather than only the aliased ones. Even together they match the specifier name and never the `from` clause, so a binding of the right name from the wrong module still passes: `rounded.oracle.ts` imports the real kernel aliased while importing its own f64 reference bare from `./rounded`, and that row is honest only because it declares the alias. Closing that last arm needs the kernel's defining module carried per row.

**Where the sweep's cost actually is**, so the cheap-looking levers aren't re-proposed. Measured 2026-08-03 on M-series/Metal: vite server boot 0.09 s, chromium launch 0.22 s, first context+page 0.77 s, each later one 0.28 s. The removable per-scenario fixed cost is the cold module-transform graph (vite re-transforming the engine through the TypeGPU plugin once per OS process) at ~1.1–1.4 s, which batch mode recovers. Three levers were rejected on that measurement: a `--dist` build (boot was never the cost, and it diverges from the dev path consumers run), parallel worker processes (multiplies the cold transform by N and contends N ways on one GPU, corrupting every timing row), and reusing one page across runs (breaks the one-verdict law and lets module singletons plus device state bleed, to save 0.28 s).

**The floor is build plus page setup, not the scenarios' frame budgets** — the reverse of what the 2026-08-03 numbers were read to imply, and measured directly on 2026-08-04. A full `bun bench --sweep` at the normal budget (`--warmup 60 --frames 240`) is 341.0 s. The identical roster at `--warmup 0 --frames 1` is 265.1 s. 78% of the sweep survives a zero frame window, so the frame budgets are the remaining 22%. Shortening them was measured and declined (below); these two wall clocks are the honest record of what a sweep costs. `shallot verify --timings` still attributes a slow or hung *single* run to a phase — it has no effect on the sweep path: `bench.ts`'s `parseArgs` has no `timings` case, and even wiring one through would print nothing, because `sweep()` calls `verifyBatch` with `quiet: true` and `spawnVerify` discards the child's stdout once the batch's JSON array is extracted, while `--timings` prints as plain lines outside that JSON. Attribute a sweep-path slowdown to build vs. frame budget with the two numbers above, or fall back to `bun bench --scenario X --timings` for a single scenario.

**A gym assert declares its own advancement.** A scenario's `assert` runs after the benchmark's profiler window, on `state` only — it cannot read the window's numbers, and in sweep mode those numbers are never printed at all (the sweep path prints only ✓/✗ and the failing check names). An assert that depends on the scene having advanced N frames but doesn't say so is an undeclared dependency on the benchmark budget happening to be long enough — latent fragility, found by diffing sweep verdicts between the normal budget and a zero-frame run and reading the two scenarios that flipped, `backend` and `raining`. The fix lives in the assert body: prefer `settle(mirror)` or a bounded await-the-condition loop over a raw frame count, and where a `frames(n)` is unavoidable, cite the mechanism `n` derives from (distance ÷ speed ÷ fixed dt, staging-ring depth, solver iteration count) in a why-comment — a number found by trying values is a tuned tolerance under a different name. `examples/gym/src/scenarios/backend.ts` (`characterGates`) and `raining.ts` (`assert`) are the shipped shape, shallot `75d13175` + `32bda90d`. **Bound the wait in the mechanism's own unit.** `characterGates` first bounded a fixed-group walk by a *frame* count — the fixed group runs well under one tick per rendered frame, so the derivation was right and the unit was wrong, leaving the pass leaning on `build()`'s frames. Derive the bound from the same constants the mechanism uses (`state.time.fixedTick`, `Time.FIXED_DT`), and never let the bound double as a pass threshold: exhausting it must fail the check. The enforcement is a **targeted short-budget run of that scenario** — `bun bench --scenario X --warmup 0 --frames 1` — not the sweep, whose budget is unchanged and so cannot see this property. The roster-wide audit, when adding a live-state scenario or during an `/audit`, is `bun bench --sweep --warmup 0 --frames 1` (~265 s, no code change, default budget untouched); `stress` fails it by construction — a 1-frame run cannot produce a pacing statistic — so that row is the expected failure, not a regression. **Wiring a shortened batch budget into `sweep()` was measured and declined** — a zero window only saves the 22% above, against standing up a second budget path plus a permanent convention every future scenario author has to honor. Don't re-propose it without a new measurement overturning the 265.1 s floor.

**CI is a decided non-goal — don't propose it.** A GitHub runner has no usable GPU (headless-shell reports SwiftShader at 4 of the 5 floor features), so it is blind to the entire real-device tier, which is where this engine's truth lives; the cross-device axis is already covered against a real Windows GPU through the WSL bridge. The OS-portability classes CI would catch are caught by `tsc`'s consistent-casing default or sit in the CLI/toolchain layer no test currently executes — which is a test gap worth closing wherever it runs, not a CI argument. The active risk is a green CPU-tier badge displacing the bench run that carries the truth.

### GPU behavior lives in Playwright, never in `bun test`

The real-GPU truth lives once, in the gym (Playwright → real device). The `render` scenario carries the forward pipeline — its `cull` mode the draw path (frustum-cull survivor counts + the slab transport round-trip explicitly, the membership gate + Mirror readback load-bearingly, its assert reading through Mirror snapshots), its shaded-look modes the framebuffer probe; the `pile` / `constraints` / `character` scenarios carry the solver. A default-suite file whose verdict depends on the device executing is **not** a tier to rely on: the lavapipe software adapter is slow, flaky, and feature-incomplete, so such tests flake by construction. A by-path `.tier.ts` that reads back through it (the headless physics probe, avbd.md) is a build/lifecycle de-risk only — the adapter's readback can prove the build ran and the poses land in closed-form, geometry-derived bands (finite, above a derived free-fall floor, at a derived rest height), never a correctness oracle and never a substitute for the real-device truth that lives here. `bun test` executes CPU-callable TGSL for kernel logic truth; `bun bench` is the only truth for its resolved pipeline on a real GPU. A kernel with a necessary raw-WGSL leaf instead uses a deterministic CPU transcription/reference for the first tier, then the same real-GPU product gate.

A unit readback's finer edges — the survivor identity / per-view slot offset / per-type scatter / Mirror staging-ring orchestration the gym's coarser assert doesn't reach — move into the gym scenario (the consolidated atom, or a narrow real-device check alongside it), not a default-suite unit readback whose verdict the device's execution decides.

### GPU evidence ladder in stage gates

Every GPU implementation or migration stage names the evidence it needs at each applicable boundary: **CPU logic**, **resolution/compilation**, **WebGPU API**, **resource**, and **product**. Omit a rung only when it genuinely does not apply, and say why. No rung substitutes for another: exact generated WGSL does not prove the pipeline validated; a shader log does not prove the target resource changed; a correct resource does not prove the final framebuffer/behavior consumed it.

Shader-side diagnostics are perturbing until a one-shot resource boundary or final-output gate agrees. TypeGPU `console.*` injects atomics/bindings and changes pipeline layout; an externally-owned pass also cannot drain it without replay. Use CPU-callable TGSL and resolved artifacts first, labeled error scopes for API truth, TypeGPU `.read()` or `probeBuffer` / `probeTexture` for a one-shot resource boundary, and the targeted gym scenario for product truth. `Mirror` remains continuous delayed telemetry, not a submission-causal probe. Record the first failing boundary and the exact shader/pipeline label + artifact hash in the active spec before attempting a fix.

**Preload — import shim, no adapter.** `tests/setup.ts` installs bun-webgpu's GPU enum constants (`GPUShaderStage`, `GPUBufferUsage`, …) so modules referencing them at module scope import cleanly. Run `bun test` from the repo root (`shallot/`), where the `bunfig.toml` preload resolves; from elsewhere, modules die at import with `GPUShaderStage is not defined`. bun-webgpu exposes a constants-only `globals()` (no adapter) alongside the adapter-installing `setupGlobals()` — the by-path `.tier.ts` arms (the physics `headless.tier.ts`, the conformance roster's physics entries) acquire their device through this preload, so the swap has a second precondition: once every pure-logic test that still bootstraps via `build()` (plugin/ECS/tween) moves to a headless `build({gpu:false})` mode or `new State()`, *and* those tier arms acquire their own adapter instead of relying on the preload's, swap the preload to `globals()` to drop the lavapipe adapter entirely, so a stray default-suite `bun test` whose verdict needs the device executing fails fast and loud instead of flaking.

### `requestGPU` policy

`requestGPU(device?, features?, preferred?)` enforces shallot's documented floor — `BASE_FEATURES` (indirect-first-instance, bgra8unorm-storage, rg11b10ufloat-renderable) plus the required `features` the active plugins declare and `maxStorageBuffersPerShaderStage: 10`. Adapters that don't meet `base ∪ required` get an `UnsupportedError` naming the missing features; this is production behavior, not a test concession. `preferred` features (e.g. `subgroups`, declared by a BVH-building plugin like physics) are requested only where the adapter has them — never gating the device, so a no-subgroup adapter still acquires. The required/preferred split is the pure `resolveFeatures` (`engine/runtime/gpu.ts`), unit-tested with no device.

Split-stage limits (`maxStorageBuffersInVertexStage` / `maxStorageBuffersInFragmentStage` and texture variants) are a recent WebGPU spec addition, so `deviceLimits` forwards each only when the adapter reports it — never hard-required. Older mobile WebGPU omits them entirely, and forwarding the `undefined` would reject `requestDevice` with a `NaN`-range error (see the `deviceLimits` comment). Mesa lavapipe reports 0 in WSL2 — present, so forwarded — which lets dev environments start cleanly while a raster consumer that actually needs graphics-stage storage fails later at pipeline creation with a clear Dawn message.

## What a change class owes

Every gate above `bun test` is priced in **`shallot verify` page boots**, not in surfaces. Measured 2026-08-26 at the WSL bridge seat, one boot costs 5.9–9.9 s across four independently measured surfaces: `bun bench --sweep` at 341.0 s over the roster `bun bench --list` prints (58 today, ~5.9 s each, sweep figure 2026-08-04), `bun run flows` at 26.46 s over its 4 flows (6.6 s), `bun run recipes` at 62.31 s over the 8 dirs it smokes (7.8 s), and `bun run test:install`'s six serial `verify()` boots at 88.77 s of a 114.33 s run (9.9 s excluding the one outlier below). A single `shallot verify <dir>` is 7.46 s, of which `--timings` accounts for ~5.22 s (70 %), the untimed remainder being bun startup plus the import graph. The surfaces are therefore not distinct cost classes to trade against each other — they are the same page boot, repeated a different number of times.

That settles the pricing question two ways.

- **Nothing is trimmed from the trigger list, and that is the criterion working.** Each surface in AGENTS.md's Verification list is the sole source of truth for its class — the install gate is the only tier resolving an install the way a user's does, `flows` the only standalone-app path, `recipes` the only dynamics smoke, `bun bench` the only real-device truth — so dropping any one is a coverage shrink, not a saving. The lever is the *selector*, never the surface: `bun bench --scenario X` / `--for <paths>`, `bun run flows --flow <name>`, `bun run recipes --recipe <name>` and `shallot verify <dir>` each narrow a roster to the boots a change can actually move. A stage gate naming a bare surface re-pays that surface's whole roster, which is the defect "A roster-wide gate is re-run only by a diff that can move the roster" names for the sweep, priced here for every surface.
- **The full roster is what no change class owes.** Running every non-unit surface once is ~605 s — sweep 341.0 + install 112.37 + recipes 62.31 + flows 26.46, plus six Playwright projects at the 10.45 s the `sandbox` project measured (the only one read; the other five — the four remaining `examples/showcase/` projects and `examples/gym`'s own touch gate — are extrapolated from it, not measured). `examples/gym`'s `gate` script runs `playwright test` directly against its dev server, a by-path driver-level gate over the `orbit-touch` scenario (real CDP touch dispatch) — a separate process from `bun bench`, which drives gym's other scenarios through `shallot verify()`, so it belongs in this roster rather than the sweep's figure. That is ~80 page boots. Quote the boot count when a spec's Validation names one of these surfaces, so the cost is legible before it is paid rather than after.

**`shallot verify examples/gym` with no scenario is not a run.** Gym's entry point (`examples/gym/src/main.ts`) renders an *index* of scenario links when the URL carries no `?scenario=`: no canvas, no `__harness`, nothing for the wait loop to sample, so it spends the full 60 s clock and reports `booted: false`, `samples: 0`, `errors: []`. That reading is the invocation, never a broken seat or a boot regression, and it cost one stage's diagnosis before the verdict said so (shallot-boot-stall-repair S1d). Every real gym caller already passes the selection — `bun bench`, `scripts/boot-cost.ts` (default `scenario=render, seed=1, warmup=60, frames=240`), `scripts/bench-tumble.ts` — so reach for `shallot verify examples/gym --query scenario=<name>`. A timeout now names its own cause on the result (`diagnosis`, `bin/verify.ts` `waitDiagnosis`): no capturable canvas, a blank one, or structure that never went still. A **fail-fast** on the first branch was considered and declined: it needs a grace threshold for how long a legitimate app may take to attach its canvas, and nothing here measures that, so it would be a tuned number gating shipped `verify` behavior for every consumer.

**`bun run test:install` is the one surface with no selector.** `scripts/install-test.ts` parses no arguments at all, so its 112 s is all-or-nothing while every sibling narrows. That is a gap in the CLI surface, not a speed lever: the gate's wall clock is real work, not overhead.

**The install gate's cost is browser boots, not installs.** Measured 2026-08-26 with a throwaway per-phase instrument: six serial `verify()` boots are 88 770 ms of a 114 330 ms run (77.6 %), while all eleven `bun`/`npm`/`pnpm install` calls together are 11 172 ms (9.8 %). Those are the two largest categories, not the whole table: the remaining ~12.6 % is the table's smaller rows (packs, builds, node-resolution probes, `tsc`) plus 5.4 % the run could not attribute to any row. A shared install cache, `--frozen-lockfile` (no fixture has a lockfile to freeze) and fixture reuse are each bounded above by that 9.8 %, and parallelising the three display-independent identity fixtures measured ~3 000 ms. No install-side lever survives that ceiling — the gate pays the same page-boot floor the sweep does. Don't propose an install-side lever without a reading that moves the 9.8 %.

**One fixture is 4× its siblings and unexplained.** `identity-browser-ejected-perturbed` boots in 39 451 ms against a 9 864 ms mean over the run's five other boots, so 25.9 % of the whole gate sits in that single excess. It is the deliberately perturbed arm (typegpu prebundled to force a duplicate identity), so the excess is plausibly the defect it exists to witness rather than overhead — but whether it is real duplicate-copy work, a retry, or a bounded wait is **unmeasured**. Any lever there trades directly against the red-proof's integrity ("A peer-identity probe brand-checks" below), so it needs its own decisive reading before anything is applied.

## Perf gates

Three axes are gated: compile/startup, GPU memory, runtime. The ladder is two kinds, and the split is by what the number actually is.

- **Exact, device-independent quantities get committed goldens**, checked by exact equality so no tolerance is invented. Three of them: pipeline count, raw pipeline-constructor calls, and GPU bytes, declared per gym scenario in `examples/gym/src/scenarios/budgets.ts` (plain data, no imports, beside `timeouts.ts` and for the same reason) and asserted both directions by `budget-coverage.ts`, the way `coverage.ts` asserts the gate map. This is the rung that catches a pipeline explosion, a doubled allocation, a variant multiplication.
- **Timings gate only as in-run ratios**, derived inside the run that reads them. `render`'s `march-cost` is the reference shape: it gates `fog:march` against `sear:color` per step, and its own comment says why a per-step ratio is the device-tolerant form. Where a row has no such ratio, the honest output is a recorded statement that the row is ungated, not a number with a made-up band.
- **Structural gates need no `isolate: true`.** A count and a byte total are immune to sweep contention, so they ride the shared-boot batch and cost no extra process. Only the ratio rung inherits the isolate law above.
- **Committed per-device timing baselines are a decided non-goal — don't propose them.** A `baselines/<device>.json` plus a tolerance band buys the one thing ratios can't see (a diffuse slowdown with no structural cause) and pays a device fingerprint, a refresh ritual, a file stale on every hardware change, and a tolerance that would be tuned rather than derived. Bench span variance is too large to gate small scenarios anyway, which is exactly where a committed number would sit.

### What each axis actually catches

Stated per axis, because a gate ladder that doesn't say what it misses reads as covering more than it does.

- **Compile/startup gates pipeline *count* and nothing else.** There is no honest per-pipeline compile-*time* instrument: TypeGPU builds every pipeline through the synchronous `device.createRenderPipeline` / `createComputePipeline`, which returns before the driver finishes compiling, so the duration recorded on that path is near-zero. `Profile.compile` is keyed by descriptor label and its count is trustworthy; `Profile.compileMs` sums scope wall spans that mean different things on the sync and async paths and is not a like-for-like quantity across a port. A **label-keyed count is only a pipeline count if every label is per-pipeline** — sear's variant labels once collided every variant of a surface onto one string, and a variant multiplication moved the count by zero. That blindness is now gated at the mechanism rather than at the naming convention: `Profile.pipelineCalls` counts raw `create*Pipeline(Async)` invocations before labels collapse, and its own exact golden (`budget:pipeline-calls`) moves for a multiplied pipeline whatever it is called. The two are deliberately **not** asserted equal — measured 2026-08-06, TypeGPU derives several raw pipelines from one named typed pipeline (`pile` 133 calls under 66 labels from a single `AvbdPlugin.warm`, `accel` 60 under 44), so an equality check would have gated three scenarios red against an invariant the post-port idiom never held. ### Freezing a golden

- **Three agreeing independent samples is the floor for freezing any measured golden**, and a gate minted below it fails as a false positive. A single-sample `render` byte golden was wrong and stayed green for two commits; two-sample reads produced three more wrong goldens that repeated sweeps caught. The ordering matters: a false-positive gate is worse than a declared exemption, because the exemption is visible in the registry while a flaky red teaches its reader to ignore it.
- **Harvest a golden through the path the gate reads** — a side instrument that produces one is a second implementation with its own bugs. A bespoke harvest script for a proposed shader-modules axis disagreed with the production sweep on 4 of 57 rows, always under-counting, because it missed TypeGPU's several-raw-pipelines-per-named-pipeline derivation that the sweep's reader already handles. Only the confirming `bun bench --sweep` caught it; skipped as a formality, four wrong goldens ship green.
- **The floor has a ceiling: a sample count measures how hard drift was to observe, never whether the quantity is exact.** `queries` held three agreeing samples while sitting exactly four stagers off its golden. Where a mechanism makes a quantity nondeterministic, no sample count makes it gateable. Sample counts settle a number; only a mechanism settles whether a number is the right thing to freeze. That ordering also bounds the floor from above: three samples price exactness in observation, and that is the right price for a golden with no mechanism argument behind it. A quantity exact *by mechanism* ships on the mechanism plus agreeing corroboration, which is why the shipped byte roster carries two agreeing samples per row (four on the seven once-exempt rows) rather than three. A third sample of a quantity already argued deterministic buys nothing the argument didn't.
- **Tighten the quantity, don't exempt the subject, and let the producer of the nondeterminism declare it.** Exempting every subject that holds a nondeterministic part shrinks the gate toward empty: per-row byte exemptions would have covered ~40 of 57 scenarios, while excluding lazy-pool bytes at the allocation site gated all 57 and recovered the 7 rows already exempt. The mark rides the allocator's own descriptor, never a label-name filter in the gate, because a filter keyed on `slab-staging` silently misses the next pool and `Mirror`'s ring was already the second instance.
- **Key an exemption by (subject, quantity), never by subject.** A ladder covering several quantities that exempts a whole row drops every exact quantity beside the bad one. A per-scenario exemption once dropped six rows' exact pipeline counts to buy six byte exemptions, and no test could red on it until the key was split.
- **Attribute a byte delta by diffing the per-label breakdown (`Profile.allocBytes`), never by reasoning from the total.** A total admits any story that sums to it, and the plausible-wrong one gets written down: a first attribution blamed view-sized render targets and was refuted by its own samples, which stepped by one exact constant twice. Equal repeated steps mean one fixed-size allocation firing a variable number of times, and that reading is what turns a delta into a source line.
- **A mark at a call site needs a per-call-site pin; the mechanism's own test won't do it.** A synthetic test that supplies the mark itself proves the consumer reads it and proves nothing about the producers. With `Profile.lazyBytes` fully tested, reverting `lazy: true` at either real allocator left every CPU-tier test green. The pin drives the real growth branch and asserts on the descriptor that reaches `createBuffer`.
- **A named gate can be broken rather than merely red, and a control run is what tells them apart** — re-baseline at HEAD with the diff parked before deciding what a mid-unit red means. The control exonerates exactly the diff it parks and no more: parking one stage and concluding "pre-exists at HEAD" reads as *not this unit's doing* while the unit's earlier stages sit inside that same HEAD. The next control (the last commit with a recorded green run) is one command away.
- **Delete a proxy gate when the property it proxies is gated at its own mechanism, and let the failing run's own instruments say which.** A CPU wall-clock p99 taken as a max over systems is a maximum-of-many-noise estimator; its bound was derived from the typical case and says nothing about the tail, so it reds ~1/10 with no regression behind it. What settled it was the co-measurement, not the rate: the same failing run's CDP GC counter read 0 GC and 0 ms pause over 266 frames at the heaviest churn, so the named mechanism provably did not fire. Read the sibling axes of a failing run before arguing about its threshold. Related: **widening a sample window suppresses a rare event's influence only if its magnitude is bounded** — tripling the window here produced a *larger* excursion than any at the narrower one.

## Diagnostics and CLI output

- **A red carrying no diagnostic is a missing instrument, never a flake.** An empty error array is not evidence that nothing went wrong — it is evidence that nothing was read, and it is the reading most likely to be dismissed: a boot arm's `[]` got a real red filed as a flake, and a sibling call site printed the same bare `[]` a whole stage later. So a red with nothing to report is its own named outcome (which predicate failed, the result's own field values, the probe behind them), distinguishable from a red that carries a diagnostic — and a check that cannot say what it saw must say *that*, under its own name.
- **A diagnostic that asserts a cause instead of reporting an observation can cost more than none.** `printSweepResult` once rendered any unparseable stdout as "verify crashed before reporting"; nothing had crashed, and 13 attempts searched for a page crash that did not exist. A caller that cannot distinguish a crash from a truncation must say what it saw (no parseable verdict array, N bytes received), not what it guessed that meant.
- **Never let `process.exit` carry a payload out.** Node's stdout to a pipe is async, so `process.exit()` truncates at the 64 KiB pipe buffer, silently and size-dependently, which reads as flaky because a concurrently-draining reader sometimes wins the race. `runVerify` awaits `flushStdout()` in a `finally` before returning its exit code. Any CLI whose output is another program's input flushes before it exits, and the pin belongs at that seam rather than on the flush primitive alone.
- **A numeric flag parser rejects a non-numeric or empty value with a throw or nonzero exit, never a substituted default.** `Number("")`, `Number(" ")` and `Number("-0")` are all `0` rather than `NaN`, so a typo silently no-ops or flows `NaN` without a `v.trim() === ""` guard *before* `Number()` — and a fix that substitutes a default satisfies "no NaN" while reproducing the defect, so rejection must be loud.
- **A claim about the measuring environment is armed, never configured.** Where a reading is valid only under a launch condition (headed, a device, a build mode), the run asserts that condition from inside the subject and fails loud, because the config that sets it can be silently defeated — a runtime `SHALLOT_HEADED=1` mutation dropped by a spawn once measured a headless page as a headed one behind every green gate, until the run read `navigator.userAgent` back and reds loud on `HeadlessChrome`.

## Production RUM reads

- **A comparability claim between a local instrument and a production metric is established by grepping the code that emits the metric, never inferred from the metric's name or the provenance of its threshold.** A metric that reads as a browser platform signal by name alone can be the product's own duration vital instead, with a different unit entirely — the two were conflated for five rounds against an unread 40-line emitter in this same repo.
- **An own-session production RUM read starts in a clean or incognito browser profile, never the reader's everyday one.** A browser extension can silently drop the RUM SDK's requests, and zero events reads identically to ingestion lag until the same session succeeds incognito.

## Harness verdict — `rendered` and the leak flag

`shallot verify`'s harness path derives `rendered` from pixels — two compositor screenshots (harness-ready and post-`run()`), OR'd, each decoded and checked for visible structure — and `harnessPass` gates on it. A green harness verdict with a blank canvas is a failed run. The load-bearing semantics:

- **Center-vs-corner, never whole-frame.** On real hardware a blank canvas carries a faint background gradient (measured 8×8 region spreads of 49–67 on genuinely blank scenes), so a whole-frame structure check passes exactly the blanks the gate must catch. Content must reach the frame center; an off-center scene is fixed by reframing the scenario, not by softening the detector. A blank read is therefore a claim about the fixture until the fixture's camera has been looked at — read the scene and the saved frame before attributing it to the engine, and compare any pixel against a value from the same colour space, since a post-tonemap clear reads nothing like its raw hex.
- **`noRender` is the opt-out** for content that legitimately draws no framed scene (GPU-compute-only, DOM-overlay asserts): declared by the app on the harness surface (`HarnessTarget.noRender`), honored by the CLI as `rendered: "opt-out"`, and always visible in run output — never a silent CLI-side list.
- **Accepted limits:** the OR means a scene that flashes structure during build then blanks at rest passes. Capture failure fails closed (`rendered: false`). Under `--memory` the post-run sample lands after the idle window, so a scene torn down at run-end can read differently with vs without `--memory` (the ready-sample OR covers it). The honesty cost per harness run: two screenshots, plus a fixed 5.2 s idle wait under `--memory`.
- **`rendered` answers *something painted*, never *this thing painted*.** Breaking a per-frame compute→vertex handoff left `rendered: true` at a centre spread of 394 against a threshold of 12, because `warnSkip` degrades the offending surface to invisible while the rest of the scene keeps clearing the detector. A paint-shaped probe cannot witness a silently unbound surface, so a producer whose output feeds one surface owes an identity assertion beside the render read — the bound buffer *is* the buffer the pass wrote.
- **A scenario's free-space claim budgets both bodies' swept reach**, and when the claim depends on another assert holding (a joint pinning an orientation), the comment says so.
- **The leak flag reads a post-run idle window, never the run window** — the benchmark retains its own stats arrays during `run()`, so a run-window slope measures the measurement. The law, which generalizes past allocation: a measurement harness's own fault never enters the subject's verdict — a staging failure, or a gate that produced no result at all, reports as a distinct *incomplete* kind, while a determined failure (a typecheck, a build) outranks an unrunnable gate, so incomplete stays reserved for a run where nothing determined the outcome. The threshold is a wall-clock B/s rate, derived and cited in place, never tuned. `gcCount` is reported, never gated — forced GC doesn't increment Performance-domain counters, so 0 is expected.
- **Red proofs, seen failing:** `examples/flows/blank` is the standing oracle — every `bun run flows` proves the pixel gate can go red, and its assert requires `verdict.ok === true` so a bitrotted fixture can't pass vacuously. `--leak <bytesPerSec>` (requires `--memory`) is the manual re-runnable red-proof for the leak sampler; nothing runs it automatically — run it whenever the sampler changes.

## Component CRUD tests

Test the **mechanism**, not every component. One test of the query pattern covers 15 components using the same pattern. Write a CRUD test only when:

- A bug was reported
- The component uses a different lifecycle pattern (lazy init, async pipeline)
- Setup runs once and might miss dynamic adds

## Reload tier

A live `State` is reused across hot reloads — a live host swaps a reloaded plugin onto it in place (`ecs.md` "Reload-safety", engine `swap()`). Reload-safety is a standing tier, mechanism-level like CRUD: one test per pattern, not per component or plugin.

- **Component identity — `bun test`.** Re-register a component with a fresh object of the same schema (what a module reload hands in) and assert membership, queries, and stored data survive by id. Mechanism test: `ecs/ecs.test.ts` "stable component ids".
- **Plugin swap — `bun test`.** A simulated `swap` preserves a runtime-set value and runs the reloaded system's new behavior on the same scheduler slot; a schema / system-set / ordering / dependency / feature change falls back to a rebuild. Mechanism test: `app/plugin.test.ts` "swap (hot reload)".
- **Rebuild-from-serialized-scene — `bun test`.** The fallback a rejected `swap` hands off to: `serialize` the live State, `build` from it with the device reused (no page reload). A runtime value on an authored entity carries over; a `warm`-derived entity re-derives once, never doubled. Mechanism test: `app/plugin.test.ts` "rebuild from the serialized scene …".
- **Failure recovery — `bun test`.** The throwing paths never wedge: a system whose `update`/`setup` throws is paused after one throw and resumes on its next swap (`ecs/scheduler.test.ts` "Failure Recovery"); a mid-swap `initialize` throw returns `ok: false` (the State is half-updated, so the rebuild fallback is the recovery); a swap against a build-skipped plugin is rejected via `App.skipped`; a failed `build()` disposes every plugin whose `initialize` ran or only started, in reverse, then the State (`app/plugin.test.ts` "build failure").
- **Survive-reload — flows.** The browser end-to-end consumer: `examples/flows/survive-reload/`, an ejected app that self-drives a real `location.reload()` and, on the restored boot, installs the published `window.__harness` asserting a runtime value restored and a `warm`-derived entity wasn't doubled. `shallot verify` drives it (its unified wait polls across the self-navigation). The app composes survival from the core atoms (`serialize`→`sessionStorage` on unload, restore via `run({ scene })` on boot) — no engine flag; the engine stays unopinionated about storage/trigger. Display-gated, `bun run flows` (`scripts/flows.ts`); `swap()` coverage is the unit tests above.
- **Per-plugin conformance — `bun test`.** `tests/conformance.test.ts` runs each roster plugin through two identical build→step→dispose passes against the same module singletons and diffs the observable signature — a double-registering registry or a doubling `warm` spawn goes red. A plugin-toggle sequence (changed-set rebuild) additionally catches a producer toggled off leaving stale registry entries; a seeded non-idempotent fixture pins the harness itself (detail in the file header). Physics/Character/Player run in the by-path `conformance.tier.ts` (the pipeline-compiling tier — their build compiles the AVBD solver's compute pipeline set) at `capacity: 8192`, the entity capacity whose contact store fits under the bun-webgpu adapter's 128 MiB storage-binding ceiling (measured; `tests/avbd/headless.tier.ts` holds the derivation). Solver math parity stays where it's deterministic: the CPU oracle + the real-GPU gym.

**A plugin earns a roster entry the way it earns a CRUD or GPU assertion** — when it introduces a new reload-relevant pattern, not by default. The trigger is carrying runtime state across a swap (a stateful `warm` spawn, runtime-set component values), a module-level registry, or a novel swap / re-registration shape; a plugin whose state is fully scene-derived is already covered by the mechanism tests above. The harness replaces ad-hoc per-plugin reload tests — grow the roster, don't write bespoke ones.

## Playwright test structure

One browser session per test file. Don't split related assertions into multiple `test()` blocks — use phases within a single test instead. Starting a new browser session is expensive and loses page state. Reconstruct state within the session if needed.

**A real-device gate display-gates on the adapter's *name*, not its floor, and says which adapter it got.** A showcase project owns its own Playwright driver and can't reach `scripts/verify.ts`'s `skipReason()`, so it probes `adapter.info` after `page.goto` and `test.skip`s on a software rasterizer (`swiftshader`, `llvmpipe`, `lavapipe`, `warp`) — before any boot wait, or the skip costs the wait's full timeout. A capability probe can't stand in: SwiftShader clears the entire base floor and 10 storage buffers per stage, then dies during execution (`mapAsync` mid-readback, or never installing the hook), which is why `voxel` crashed here for a release cycle — the `gpu-particles` recipe reaches `skipReason()` through `scripts/recipes.ts` and skips before the dispatch. Keep the pattern narrow and log the adapter on both paths — an over-broad match reports green having tested nothing, and a silent skip is the same defect as a crash. Not every gate earns it: `visualization`'s desktop gate genuinely passes on SwiftShader, so it stays ungated — its touch smoke does not (2026-08-26, `hasTouch` mobile context under SwiftShader: `createBuffer` 1.3 MB `mappedAtCreation` failure, device destroyed), so that one carries the skip.

## Pairwise testing for combinatorial GPU features

Most bugs come from 2-factor interactions. For combinatorial feature spaces (surfaces × pipelines × opaque/transparent × shadow × instance fields), generate pairwise test matrices (~40-60 combos instead of thousands). `compileVariant` compiles a surface's color-pass pipeline(s) (memoized by name + variant) — feed it pairwise inputs, validate structurally + GPU-compile.

## Structural validation over visual regression

Prefer the smallest applicable observation ladder: (a) CPU-callable TGSL or structural validation of generated WGSL, (b) exact resolved WGSL + compilation/API validation, (c) one-shot buffer/texture resource validation, and (d) the final gym observable. CPU cross-validation is optional only where no meaningful pure oracle exists. Reserve screenshot comparison for integration-level Playwright tests. Structural tests are fast and pinpoint failures, but never promote them into real-device evidence.

**Structural validation runs on the whole kernel corpus, not per-test-file opt-in.** `tests/standards.ts` + `tests/standards.test.ts` enumerate every TGSL kernel under `src` (the `examples/` tier keeps its per-test-file opt-in; app-tier, gated separately) mechanically — walk, dynamic import, TypeGPU's own `isTgpuFn`, identity-dedup, `tgpu.resolve` — rather than a hand-maintained call-recipe registry per `*Wgsl()` seam; `tgpu.resolve` needs no such recipes, confirmed on all 255 exported symbols standalone. The walk yields 101 kernels, frozen as an exact golden, each held to the discipline checks above and answered in a differential registry (`{ test }` / `{ reason }` / `{ gap }`), both asserted both directions — a kernel added tomorrow reds the population golden before it can land untested.

Three limits worth naming before reading `DEFAULT_CHECKS` as full coverage. `isTgpuFn` excludes compute/vertex/fragment entry points, and `src` exports none today — that arm is unexercised, and the day one is exported it leaves the population silently. `noDivision`, the stronger check for index-only arithmetic, stays inert corpus-wide until a kernel opts in via its registry row's `also` — `DEFAULT_CHECKS` excludes it deliberately, or every legitimate float division would red. And `callsSymbol` alone proves only call-position syntax; `importsSymbol` closes most of that residual (the exemption clause above), leaving the wrong-module import arm open, and together they prove a call happened, not that its result is asserted against a reference.

## `.test.ts` vs `.oracle.ts` vs `.probes.ts` vs `.tier.ts` vs `.lab.ts` vs `.playwright.ts`

The suffix is the tier — bun only auto-discovers `.test.`/`.spec.`, so a different suffix opts a file out of the default `bun test` while staying runnable via a `./`-prefixed path.

- **`.test.ts`** — spec tests. First principles, conservation laws, tight tolerances. Permanent. Run by `bun test`. If one fails, the code is wrong. The fast inner loop — keep it lean.
- **Per-file speed cap.** A `.test.ts` file whose tests run longer than 5 s reds in `bun test` itself — a preload in `bunfig.toml` enforces it with no wrapper to forget. The cap measures a file's test time (from its first `beforeEach` to its last `afterEach`), not its wall time: module evaluation and `beforeAll` sit outside the window. Two responses to a red, and only these two: (1) derive the scan's size from the property it states — an arm whose own comment claims invariance in N has no reason to run at N; (2) promote the slow arms to a by-path tier — a sibling file named `.oracle.ts` or `.tier.ts`, with the reason in its header, run by path when touched. Raising the cap or exempting a file in place is not a response. **Read a red under load before responding to it.** A wall-clock duration measures the host as much as the file, and this cap has a known false-red mode: once (2026-08-26) a load-inflated 39 s `bun run test` reddened `tests/conformance.test.ts` against the 5000 ms cap, while two runs of the identical checkout at 14.8 s and 12.9 s were green at 3042/3042 — the red discriminated concurrent load, not the artifact, and three suite runs were spent telling them apart. So re-run a red file alone by path first — the cap's own message says to, so nothing depends on a reader having found this paragraph. A red that reproduces in isolation is the file's, and the two responses above are the only two. **A red that does *not* reproduce is the weaker outcome, not the clean one**: it says the host was loaded, and it says the file has so little headroom that ordinary load crosses the threshold. Isolation diagnoses; it licenses nothing, and it is not a third response — a file waved off by repeated isolated re-runs is being exempted per incident, which is the same move as exempting it in place. Nothing here can currently tell a one-off from a file creeping toward the cap, because that needs a *distribution* and this repo records none. **Reversing the cap to a recorded reading plus an opt-in throw is the shape that answers both the false red and the creep, and it is unavailable today**: that shape needs a recorded per-file distribution some reader consumes, and this repo has no such sink — committed per-device timing baselines are a decided non-goal (above). Dropping the refusal now would drop the reading with it, and coverage moves tiers, never shrinks. The condition is the sink: when a recorded per-file distribution exists with a consumer, the refusal becomes a notice; until then it stands (verdict 2026-08-26). Every by-path suffix in `TEST_TIER_SUFFIX_NAMES` skips the cap by matching its own suffix — exemption is derived from the path, never listed — but only `.oracle.ts` and `.tier.ts` are promotion destinations: `.probes.ts` is the browser-launching gate tier and `.lab.ts` is temporary.
- **`.oracle.ts`** — the heavy deterministic CPU reference tier (the f64 AVBD physics oracle, `tests/avbd/`). Permanent and load-bearing — the executable spec every GPU physics gate is validated against (avbd.md "the oracle is not the suspect") — but slow (hundreds of f64 sim frames per test), so it's split out of the inner loop to keep `bun test` fast. Run it **by path, when you touch AVBD or physics** — `bun test ./packages/shallot/tests/avbd/*.oracle.ts` from the repo root — not as a routine pre-commit sweep. A script name is sanctioned routine, so a command earns one only for the iteration loop or the standard gate for a change class — a per-kernel, slow, or occasional gate like this tier stays script-free and by-path, or it becomes a slow default suite. `scripts/check-scripts.ts` enforces the split in `bun check`, asserting both directions that every declared script resolves and every root script is cited. The `./` prefix is load-bearing (a bare path is a name filter to bun); the shell expands the glob, so it reaches `tests/avbd/` only. A new oracle-tier file just needs the `.oracle.ts` suffix there.
- **A test outside the default gate's explicit paths is a tier only if some gate runs it.** The root `package.json`'s `test` script (`bun test packages/shallot scripts evals site examples/showcase/visualization/test`) declares the default-gate cone, so a `*.test.ts` written outside those paths runs nowhere until a by-path gate names it — otherwise it's an orphan, never executed.
- **A test-population sweep's own glob is a granularity claim.** `**/*.test.ts` is the wrong one wherever a real differential lives in a slower tier: the TGSL differential registry's queue globbed only `.test.ts` and reported two kernels as gaps that in fact carry real CPU differentials in `.oracle.ts` files above — the tier this file already calls "the executable spec every GPU physics gate is validated against." Enumerate every tier named in this section, not the default suite's own discovery rule. **A coverage read is the same instrument with the same blindness**: bun's reporter lists only modules a test loaded, so a file nothing imports is *absent* from the table rather than sitting at 0%, and the least-covered files are exactly the ones a per-file percentage drops. Walk the population mechanically and diff it against the instrument's own output; the two files this caught were the two the coverage-derived work list omitted.
- **`.probes.ts`** — permanent gates that launch a browser (`bin/verify.probes.ts`, the `--timings` harness-install + resource-timing probes). Same reason as `.oracle.ts`: real and load-bearing, too slow for the inner loop — and a Chromium launch inside the parallel default suite flakes. Run by path when you touch the probes: `bun test ./packages/shallot/bin/verify.probes.ts`. The pure half stays in the neighbouring `.test.ts` as the sentinel. The suffix also ships nothing — `check-pack` rejects it and `package.json`'s `files` excludes it, both needed since a non-`.test.ts` test file otherwise packs.
- **`.tier.ts`** — a corpus-scale gate split out of the default suite for speed; coverage moved tiers, not shrunk — a sentinel stays behind in the default suite against the same frozen fixture. bun does not discover it (only `.test.`/`.spec.`), so it runs by path: `bun test ./examples/showcase/roads/src/editCorridor.tier.ts` from the shallot root. Advisory cue, not a mechanism — nothing consumes the list to run it; which edits mean run it is the tier file's own header (its transitive import cone, walked there), so read that header rather than a registry.
- **`.lab.ts`** — investigation files. Trace internals, compare against references, probe edge cases. Not discovered by `bun test` — run manually (`bun test ./packages/shallot/tests/foo.lab.ts`). Temporary — delete or promote when done.
- **`.playwright.ts`** — showcase Playwright specs. Each showcase project under `examples/showcase/` owns its own Playwright driver and writes its browser-driven gates under this suffix (the roster drifts as projects are added — read the directory, not a list here). Not discovered by `bun test` (only `.test.`/`.spec.` are), so it opts out of bun's widened `root = "."` discovery — which is why these specs carry this suffix rather than `.spec.ts`: a bare `bun test` collects `.spec.ts` files, and these error under bun. Run by path through the project's own Playwright config (`bunx playwright test` from the showcase project root, or `shallot verify`).

This roster is one exported constant, `tests/test-tiers.ts`'s `TEST_TIER_SUFFIX_NAMES`, asserted against this section by `scripts/check-docs.ts`'s tier-suffix roster arm, so a suffix is added in one place. The arm's population is every tracked file, including a consumer's own test file, but its *detection* is two written shapes on one line — regex alternation and an array literal — so it catches the restatements that have actually occurred and not the class: a roster spread across lines still evades it, and that boundary is the arm's, not a reason to re-list the suffixes anywhere.

## A fresh checkout's `bun test` count isn't a floor yet

Four fixture trees live outside the commit, so a fresh clone or worktree silently runs a smaller suite than an established one. Measured 2026-08-10: 1826 pass / 33 fail where the populated tree read 2632 / 0. Place all four before quoting a count as the floor a later run is compared against. A worktree also needs its own `bun install` inside `shallot/` — without one every test file dies at import and the suite reads 0 pass / 157 fail, which is a provisioning failure wearing a red suite's clothes. **A build measured in the working tree is not evidence about a clean checkout either, and this error runs green-when-red** — six ejected consumer demos built in 3.7 s in-tree while all six failed from a pristine clone on the gitignored audio wasm they import transitively. **A gate clause reading build output skips green in a pre-build checkout**, so such a clause owes a `*_REQUIRED=1` arm that reds on the absent artifact rather than skipping.

- `packages/shallot/rust/audio/pkg/` — the gitignored wasm build artifact. Absent, five registry/standards tests fail on an unresolvable import, which reads as real red rather than a missing fixture. Build it, or copy it from a populated tree. A missing build artifact blocks every gate that shares its import graph, not only the one gate you measured — this one takes `bun check`, the whole `bun test` population that imports it, **and** `bun bench` plus every `shallot verify`-driven run, whose page dies on a vite 500 while the run still reports `hardware: apple / metal-3`. Read a real-device gate's failure for the artifact before the adapter, since a present GPU beside a dead page looks exactly like a display gate and is not one.
- `packages/shallot/tests/fixtures/avbd/` — gitignored, ~161 MB. Copy it in.
- `examples/gym/public/sponza` and `examples/gym/public/gltf-samples` — local-only mounts into `reference/` in the author's workspace layout, outside the repo (sponza → `reference/sponza-optimized`, gltf-samples → `reference/gltf-sample-assets/Models`). Not submodules and not fetchable: symlink or copy them in. Absent, the `render` scenario's gltf modes and the `gltf` scenario skip with a clear message naming the missing assets — `bun bench` checks the filesystem before booting a page, so the skip is instant and announced, never a 60s ready timeout. It is the quietest of the four, because nothing in `bun test` reads it.
- The glTF corpus, a submodule at `reference/gltf-sample-assets` in the author's workspace layout, outside the package (`git clone https://github.com/KhronosGroup/glTF-Sample-Assets reference/gltf-sample-assets` — runnable from a plain shallot checkout). Its absence is the dangerous one: 292 conformance tests degrade to an announced skip that no fail count shows. Run the required arm, `GLTF_CORPUS_REQUIRED=1 bun test`, so an absent corpus is red instead of quiet. **An unprovisioned run's pass count is the only half that moves**: the corpus's suite presence-gates down to a handful of arms rather than vanishing, so file count and fail count read identically while pass drops (2745 in a worktree against 3036 on the same trunk, 2026-08-26). Reconcile a shortfall against those two invariants before reading it as a regression.

## Bumping a dep many packages pin, bump it everywhere at once

One GPU dependency is pinned at many independent sites, and a partial bump is worse than no bump: the unbumped packages nest the old copy under their own `node_modules`, and the two copies' branded internals disagree, so `bunx tsc` reports hundreds of phantom `[$internal]` errors that read as a broken migration rather than a broken install. Measured on the 0.11 → 0.12 TypeGPU move (2026-08-14): typegpu and `unplugin-typegpu` are pinned across the engine package, the scaffold, the root eslint plugin, and the example/showcase/flows projects, and the plugin versions move with the library, never independently. **This roster is enumerated by the gate** (`scripts/check-docs.ts`'s manifest-pin arm), not maintained by hand.

- Edit every site in one commit, then re-resolve the lockfile and **confirm the tree before reading any gate**: `find . -path '*/node_modules/typegpu' -not -path '*/node_modules/*/node_modules/typegpu/*'` must return the root-hoisted copy alone. A stale nested copy invalidates every type error and every runtime failure you are about to read.
- The bump is not done until the example projects that pin their own copy are bumped too. `bun test` and `bunx tsc` never reach them; `bun bench` and `bun run flows` do, and they fail late.
- **The docs are a pin site, and they fail latest of all — in a stranger's terminal.** The 0.12 bump hit all six manifests and left `packages/shallot/README.md` and `MIGRATION.md` documenting `typegpu@~0.11.9`; both ship in the tarball, so the install a stranger is told to paste resolves to a peer conflict or the duplicate identity that dies at pipeline warm. No gate read those lines, which is the same hole `check-versions.ts` was written for one release earlier. `check-docs.ts` now reads the three tracked pins from the manifests that declare them and compares them against every fenced `bun add` line in the repo's docs. Its scope is a command a reader runs, never prose: `CHANGELOG.md`'s dated `typegpu@~0.11.9` is a historical fact about what 0.9.0 shipped, and a blanket sweep moving it would be wrong in both directions.

## Tolerance tiers

- **Exact:** no floating-point reason to differ (mass invariance, quaternion normalization) → `1e-10` or tighter
- **Truncation error:** derive from integrator order + step size, not continuous-time physics
- **f32 precision:** `~1e-6` relative for single ops, accumulates with chain length
- **Solver convergence:** derive from iteration count + penalty schedule, not observation

## Install gate

`scripts/install-test.ts` (`bun run test:install`) is the only tier that resolves an install the way a user's does: it packs the engine into a tarball and `bun install`s it into a throwaway project, never a workspace symlink. **Evaluation infrastructure:** `bun run evals/setup.ts` and `bun run evals/grade.ts` are repo-internal tools that prepare and test eval tasks; they run path-invoked, not as declared package.json scripts. A local checkout or a dev link resolves *outside* `node_modules`, so Vite's dependency scanner never prebundles it — a whole class of packaging defect (a missing `optimizeDeps` exclusion, a duplicate TypeGPU identity) cannot occur under a linked install, and no gate run against one can see it. Any fixture added to this tier installs from a pack, not a link. What the gate costs and why no install-side lever survives is priced once, under "What a change class owes" above — don't re-derive it here.

- **Boot a real browser, not just a build.** A clean build proves resolution and bundling; it says nothing about whether the installed engine's pipelines survive first paint. The gate's real-device rung (`verify()`, guarded by `skipReason()` where no display is available) is what catches a runtime warm failure a passing build hides — omit it and the tier is structurally blind to that class.
- **A check for the package's importability under a non-bun runtime is only as honest as its reader, and both convenient readers lie.** `Bun.build` *drops* an external JSON import's attribute, so a bundled arm reds identically on fixed and broken source, and `jiti` rewrites the import to `require` and greens on the defect — only a real spawned `node` reading the source as shipped can answer, which is also why no bun-side gate can see this class. Guard the arm's *subject* too: assert it realpaths into `packages/shallot`, or a stray extract at the repo root greens it against a published artifact while the tree stays broken.
- **A documented recipe is a fixture, not a claim.** The gate's roster of hand-assembled projects is not the product's install population — the recipe a doc tells a stranger to paste is. `ejectedFlow` reads `MIGRATION.md`'s ejected-Vite block straight out of the doc and boots it verbatim rather than a hand-typed stand-in; a recipe nobody boots this way is untested no matter how many hand-patched variants pass around it.
- **A dogfooded consumer's render is verified by a person running it, and a still is only supporting evidence.** Exit codes cannot see "renders green but wrong", but neither can a frame the agent chose to capture — a `--shot`-style still says boot-plus-first-render and nothing about the phases past it, so the stage's job is to leave the consumer runnable and hand over its own documented live command beside the still. **Open a still through a real decoder before handing it up** (a hand-rolled PNG encoder emitted raw deflate where PNG needs zlib, and its own check counted *compressed* bytes as non-zero pixels, so an unopenable file arrived with a green self-report). A target with no image-writing gate is accepted on exit codes plus the live run: say that, rather than implying its render was looked at.
- **Assert the artifact's surviving structure, not source text a build can erase.** A marker grepped for text that bundling inlines or removes can never fire on the leak it names. Check what the artifact actually still carries — its remaining top-level import set against the declared externals — and confirm the check is non-vacuous by reading what it finds before trusting it green.
- **A display-gated rung owes a display-independent sibling for the part that needs no device.** A check placed only after a `skipReason()` guard reports green on a display-less host without ever running. Where a property doesn't need a GPU — a compiled export resolving and actually exporting a real symbol, not merely failing to throw, or a peer-identity brand check (below) — assert it in a plain-Node check placed *before* the skip, so a headless host still exercises it. The same law bounds a perturbation arm: a page that dies at import resolution before publishing its verdict, or a dependency discoverable only at runtime inside a fast-teardown harness, produces no observable at all — catch both only with a control reading `false`, never by reasoning about the harness.
- **A rung too expensive for the suite is a documented manual premise, not silent coverage.** A native `shallot build --target` from a packed install compiles the `rust/window` crate through cargo and downloads the CEF runtime on the first portable build — minutes either way — so this tier holds only the cheap layers (the packed-file assertion, the crate-present-after-install check, and the ENOENT-guard arm that needs no toolchain) while the compile itself is run by hand whenever the packaging surface moves. Say which layer a check covers: a presence check reads as coverage of the compile it merely precedes.
- **A peer-identity probe brand-checks, it doesn't version-compare.** A dependency's brand markers are per-copy `Symbol(...)` (never `Symbol.for`), so `isTgpuFn`-shaped checks imported from a consumer's own resolution read `false` against a foreign copy even at an identical version string — `__TYPEGPU_AUTONAME__` failed this way as a boot-time alternative (its control left a same-copy fn's name unset too) and stays rejected without a red-and-green harness. A duplicate-copy fixture must pin two *distinct* versions under pnpm, whose content-addressable store collapses an identical-version alias to one physical entry and silently turns the red arm green. Confirmed on typegpu: shallot's two boot paths (zero-config sandbox, ejected Vite recipe) both brand an engine-built canary `true`, so its `optimizeDeps` exclusion is a defensive default, not a load-bearing dedupe.

## Release gate

`scripts/check-versions.ts` (in `bun check`) holds every version site to `packages/shallot/package.json`: the two package manifests, `rust/{audio,window}/Cargo.toml`, both `bun.lock` workspace entries, `CHANGELOG.md`'s newest heading, and the `tree/v<version>` links in `README.md`'s demo table. Add a site here the moment one exists — 0.9.1 published with a stale `bun.lock` and no changelog entry, both because no gate read those files.

- **Cycle order, every release:** bump every version site first (one edit per site — `check-versions.ts` enumerates them), then `bun run scripts/check-versions.ts --release` before the pack, then the RC dogfood, then publish **both packages** — `@dylanebert/shallot` and `create-shallot` share the version, so a publish naming only the engine leaves the scaffold a release behind, then `bun run demos` (the site demo release gate — builds every showcase demo against the published package and verifies each renders on real hardware; a skip is not green), then merge to `main`, and tag — publish and tag land together. The changelog's newest heading is a version site, so a consumer-visible change landing between cycles has no legal entry until the bump — the first step after bumping is writing the deferred entries.
- **The RC dogfood is standing practice, not a one-off.** Pack the candidate and install the tarball (never a link — `install-test.ts`'s law above) into real consumer projects, then run their own gates against floors recorded *before* the pack. A cycle where it finds nothing is not the argument against it: it is the only gate that sees the consumer-install class 0.9.0 shipped three of, and it costs about an arm-hour per consumer.
- **A consumer install found in place is usually a link, so the floor has to be built rather than read.** Three of four consumers at 0.9.3 carried hand-made symlinks into `packages/shallot`, one of them into the release candidate's own source, so a floor taken as found measures the RC and reports it as the old version — and a link has no `dist/`, which reds a consumer's gates for link-shaped reasons that then "heal" on the tarball. The only honest floor is a registry install of that manifest's own tracked pin.
- **A consumer install is the tarball plus the release's declared peer range, and an install moving only shallot says nothing about the release.** A stale `unplugin-typegpu`/`typegpu` minor — in the pin or merely in `node_modules` — reds at GPU pipeline warm with `booted` and `rendered` both still true, so read the *installed* peer version before believing any red. Order matters: **every dev and peer add first, the tarball last**, because `bun add` of any package silently re-resolves the whole manifest and replaces a by-path tarball with the registry version the tracked pin names — re-read `node_modules/@dylanebert/shallot/package.json` *after* the last install command, never once at the start. Where a lockfile still resolves the old version, `bun install <tgz>` fails with a dependency loop; `bun remove` then `bun add <tgz>`.
- **A dogfood stage ends with the consumer runnable and its tracked tree clean, and a clean `git status` is not the whole check.** Restore manifests and lockfiles from pre-install copies (the RC stays live in gitignored `node_modules`, which is what leaves the consumer runnable for the person's render check), read the superproject's gitlink too where the consumer is a submodule, and remove any package the stage installed into a shared workspace root — an undeclared copy there is invisible to `git status` and silently satisfies a later consumer's upward resolution. Capture pre-existing gitignored stills before the first gate run: a consumer's bench may `rmSync` its own shots dir on entry.
- **Comparing version sites to each other cannot see a bump that never happened.** A whole cycle run against an unbumped tree is uniformly green until npm rejects the republish, and the tell (a pack named `…-0.9.0.tgz`) lands in the dogfood evidence where nobody reads it. `bun run scripts/check-versions.ts --release` is the arm that reds on it — an existing `v<version>` tag means this version already shipped. Run it before the pack; it is release-time only, and reds by design on a tree sitting at its last release.
- **A doc's claim and the gate that would catch it are two different artifacts.** `check-versions.ts` pins the migration guide's title and its install line and cannot see the sentence *between* them naming a different target — which is how a 0.9.4-gated guide shipped saying 0.9.3, alongside a changelog bullet promising a tarball placement `prepack.ts` gates against and an npm README promising a prebuilt download the build never attempts. A version site is gated; a claim about behaviour is not, so a release's prose is re-read against the artifact it describes, not against the gate that greened beside it.
- **`MIGRATION.md` is not a version site.** Its title and install line name the minor the guide targets — a micro never changes what the guide says, so nothing in it moves on a patch release (a new guide exists only if a major/minor breaks something). Prose dating a change to the release that shipped it ("ships compiled as of 0.9.1") is a historical fact, so a blanket stale-version sweep over that file would be wrong in both directions.
- **A gitignored lockfile is not a version site.** `rust/audio/Cargo.lock` is gitignored build output — cargo rewrites the own-package entry from the manifest on the next build — and `rust/tumble` is `publish = false`, versioned independently of the release. `rust/window/Cargo.lock` is tracked, not gitignored.
- **A workflow record is keyed by path, so a new file reusing a retired workflow's filename inherits its disabled state and never runs, with no error.** The site deploy therefore lives at `.github/workflows/site.yml` and must never be `pages.yml`, whose record from the deleted docs site survives in a disabled-manually state — a silent no-run that reads as a green stage.
- **Confirm the deployed site reports the released version.** The site workflow deploys on tag push `v*`; once it completes, `dylanebert.com/shallot/` must show the tag's version in its label. A page serving the previous version means the deploy didn't land — the release's public face is stale, and no local gate catches it.
- **Verify the release assets exist after tagging.** The release workflow attaches the six prebuilt archives (`shallot-window-<target>-<mode>.tar.gz` for the 3×2 matrix) plus a top-level `SHA256SUMS` to the `v<version>` GitHub Release. After the tag push, confirm all seven assets are present: `gh release view v<version> --json assets --jq '.assets[].name'` must list the six archives and `SHA256SUMS`. A missing asset means the prebuilt download path falls back to lazy compile for that cell — a silent regression no local gate sees. **Verify the checksum file against the bytes it covers** (`gh run download`, then `shasum -a 256 -c SHA256SUMS`) rather than trusting the two artifacts because both are attached; The release-*creating* branch first completed a real tag push at `v0.9.4` (2026-08-24: `checksums` green with no release pre-created, all seven assets attached, `shasum -c` verified), so the reading exists — but it is one reading, and it took a `GH_REPO` fix to get: **a release or consumer path whose gate has never traversed it is untested regardless of the gate's colour**, and the tell is an asymmetry that keeps the safe path safe (a dry-run guard, a doc's default config, a subpath export) while leaving the real path unread. Every version through 0.9.3 published green over a job that could not talk to its own repo. The end-to-end proof lives at `bun run scripts/e2e-prebuilt.ts` (attended seat with `gh`): it uploads a dry run's artifacts to a draft prerelease, pre-populates the cache, and runs `shallot build --target linux --portable --release` with `cargo` shimmed to a failing stub, proving the prebuilt path needs no Rust toolchain.

## GPU timestamps, not FPS

`requestAnimationFrame` measures CPU, not GPU. WebGPU's `queue.submit()` returns immediately. GPU timestamp queries measure actual hardware execution time — this is the primary benchmark metric.

**CPU timing quantizes to 100 μs in non-isolated Chrome.** `performance.now()` returns multiples of 0.1 ms without COOP+COEP isolation, so per-frame samples bin to {0.0, 0.1, 0.2 …}. `min` over samples becomes biased toward zero; **avg over ~200 frames is the correct primary stat** for CPU-mixed measurements (the gym `extras/profile/benchmark.ts measure()` rig follows this — 60 warmup + 500 measured frames, avg as primary). Read avg for CPU-mixed rows, min for pure-GPU timestamp rows (sub-μs, one-sided noise).
