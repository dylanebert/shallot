# Exports

## Tiers

- **`@dylanebert/shallot`** — the engine's public API (re-exports engine + standard + extras). The happy path (`Part` + `mesh()` + `Camera` + the default plugins), the platform primitives (`slab`, `Inputs`), and the renderer (`RenderPlugin` / `SearPlugin` / `GlazePlugin`, `lit`). `DEFAULT_PLUGINS` is the zero-config set (`standard/defaults.ts`). Contract: `render.md`.
- **`@dylanebert/shallot/extras`** — the author-facing convenience + debug plugins (`orbit`, `lines`, `outline`, `sprite`, `text`, `animation`, `profile`, `sky`, `cells`, added per-scene) plus the glTF importer (`loadGltf` + `placeScene`; add `GltfPlugin` — scenes reference primitives by name (`part="mesh: model.glb#0"`, imported by its preloader + decorated by its route sync), the utility itself stays one-way and creates no entities; its decode/cache/tooling surface is `gltf/core`) and the live joint-palette skinning substrate (`SkinPlugin` + the `Skin` component + `LiveSkin` + `skinMatrix` — the engine-owned runtime substrate glTF, physics, and scripted producers all pose through; it provides no surface, so a producer registers its own over the WGSL on `skin/core`). Also reachable on the bare barrel. The boundary is engine-substrate vs author-convenience, **not** default-vs-opt-in: opt-in engine capabilities (`audio`, `mirror`) and libraries (`bvh`) live in `standard/`, not here — `standard/` ⊋ `DEFAULT_PLUGINS`. `extras/index.ts` star-exports every module that has a barrel-worthy public API — each module's `index.ts` owns its clean public API (internal/test-seam siblings: "Barrel rules" below). `cells` (the ASCII-native render target, `shallot-tui` spec) is `CellsPlugin`: add it to a camera-bearing scene and, after the scene renders, a compute pass samples `view.framebuffer` into a structure-first-selected cell grid (edge-tangent directional glyphs, coverage-ordered fill fallback) that an instanced draw renders back into the same offscreen target before glaze composites it — the GPU cell-grid contract stays on `cells/core` (no author-facing surface of its own).

An ejected config imports `unplugin-typegpu/vite` directly when it needs options such as post-framework `.svelte` / `.vue` inclusion, then adds `projectPlugin(dir)` — the argument is load-bearing: omit it and `virtual:project` resolves to an empty manifest (default plugins, no scene). ## Compiled tooling exports

Every export ships raw `.ts` source, except two: `./vite` (`src/project/vite.ts`) and `./harness/browser` (`src/harness/browser.ts`). The reason every other export stays raw — the mandatory TypeGPU transform must see engine source untransformed inside `node_modules` — doesn't reach these two, because their only consumption context is Node: a `vite.config.ts` and a `playwright.config.ts` both resolve through Node's plain ESM loader, which applies no TS transform to a `node_modules` import and throws `ERR_UNKNOWN_FILE_EXTENSION` on raw `.ts`. So the boundary is by consumption context, not a blanket rule: **runtime exports ship source because the transform must see them; Node-reachable tooling exports ship compiled `.js` because Node must load them.**

Both `exports` entries are conditional — `{ "types": "<the .ts source>", "default": "<the dist .js>" }`. `types` is a `tsc` type-checker convention, not a runtime resolution condition: only `tsc` reads it, so type-checking still resolves to source (no `.d.ts` emit, no type drift), while a bundler (esbuild, Vite) resolves straight past `types` to `default` — it never falls back to source. That's harmless here only because nothing bundler-consumed imports `./vite` or `./harness/browser` through this package's `exports` map today; a bundler-reached consumer of either would get the compiled `.js`, not source. The build is `scripts/build-tooling.ts`, run by `prepack` alongside the examples projection; `dist/` is gitignored and removed by `postpack`, never committed. `src/project/` (the `./vite` island: `vite.ts` + `assets.ts` + `engine.ts` + `generate.ts` + `manifest.ts`) is closed — node builtins plus the `vite` / `unplugin-typegpu` externals it imports, no engine runtime, no TGSL — so compiling it carries no duplicate-TypeGPU-identity risk; `harness/browser.ts` has no imports at all. Adding a third Node-reachable tooling export means adding it to `build-tooling.ts`'s entry list and giving it the same conditional `exports` shape, not reaching for a raw `.ts` default. `./harness` is the one dual-context export this conditional shape does NOT cover — bundler-consumed at runtime (raw `.ts` so the TypeGPU transform sees source) AND Node-consumed from a Playwright spec (raw `.ts` throws `ERR_UNKNOWN_FILE_EXTENSION`) — so it stays a raw `.ts` mapping while only `./harness/browser` takes the conditional shape; do not apply the {types,default} recipe to it blindly, that hands a bundler compiled `.js` instead of the source the transform must see.

**A linked dev checkout needs `dist/` built once before either export loads through the package's `exports` map** (`playwright.config.ts`, a plain node script, `bun pm pack`'s own install-gate consumer). The `default` condition points at `./dist/*.js` unconditionally, with no fallback to source, so a fresh `bun link` / workspace checkout that hasn't run `bun run scripts/build-tooling.ts` (or `bun pm pack`, which runs it via `prepack`) resolves to a missing file. This is not a Node-only hazard — `default` is the condition bun and every bundler resolve too, so a bun-side importer of `./vite` or `./harness/browser` against a dev link hits the same missing file. It bites where a link and a specifier import meet: a consumer whose `playwright.config.ts` imports `./harness/browser` by specifier, run against a linked dev checkout rather than a registry install. In-repo code that needs either module imports the `.ts` source by relative path instead (`bin/verify.ts` → `../src/harness/browser`, `bin/dev.ts`/`bin/build.ts` → `./project/vite`) — it never resolves through the package's own `exports` map, so it never hits this.

## Distribution layers

Two layers, drawn on purpose; the boundary is load-bearing.

- **The tool (canonical, inner).** `bun install @dylanebert/shallot` + the `shallot` CLI, used inside a standard web dev project with any framework. Shallot is a tool/package, not a framework — the CLI reads shallot files (scene, manifest, plugins) in any layout; the user's own bundler/framework owns preview. First-class; never traded away for a convenience layer.
- **The convenience bundle (outer).** Bundles the canonical path into a frictionless experience (a standalone app, a future live-authoring host). Its own folder (not `src/`), depends **purely inward** on the tool + engine, and **composes** the tool — never duplicates or reimplements it. Inward core: the headless project-resolution substrate (read manifest → resolve plugins → load scene, no vite/browser).

For engine/core code under `src/`: stay unaware of the convenience layer. Dependencies point inward, never outward; a convenience-only concern reaching into `src/` is the inversion to reject.

## Barrel rules

Each plugin barrel (`index.ts`) exports its public API:

- **Barrel:** components, singletons, registration functions, types that game developers use.
- **`*/core` subpath:** WGSL constants, shader compilation, GPU buffer packing, internal mesh/surface queries.
- **Neither (internal):** implementation details consumed only within the module. A module-internal export
  shared across sibling files (or a test seam) lives in a sibling file imported directly, never re-exported
  from the barrel — orbit's `OrbitSmooth` (`smooth.ts`) is the shape.

The barrel and component schemas are the public surface agents and consumers read directly (JSDoc, reflection),
so an export or field decision **is** a documentation decision: a field a scene author can't act on doesn't
earn a public row (move it to internal derived state), a default that reads as float garbage gets a principled
value in code, and every release-public export carries JSDoc (lowercase, one line, `@example` on most
callables, definition site not barrel). Before removing any export, grep every tier for consumers — `src/`
AND `examples/` — and confirm each hit is load-bearing by reading the call site, not just the reference.

Cross-module imports within `standard/` use relative paths. Producers (the `extras/` viz plugins, external plugins) import from `./render/core`.

**`sideEffects` (tree-shaking).** `package.json` lists the only side-effect modules so the barrel shakes — import `Part`, ship no `audio`/`gltf`. A module with an import-time side effect (today just `standard/defaults.ts`: the `DEFAULT_PLUGINS` + default-loading injection) must be listed, **and so must any barrel that re-exports it via a bare `import` for that effect** (`standard/index.ts`) — named imports resolve straight to source modules and skip the barrel body, so an unlisted side-effect host is silently dropped (a `defaults: true` build then renders nothing). Exact paths only; bun <1.3 deopts on wildcard globs.

**Physics backend packaging — tumble default, avbd swap-in.** Physics is opt-in (out of `DEFAULT_PLUGINS`), but *when* a scene uses it, tumble is the default: `TumblePlugin` + `Tumble` ride the **main barrel** (`standard/index.ts`), and the engine itself is **inlined source** — `standard/tumble/engine/` with a committed base64 wasm kernel, no runtime dependency to install or resolve (`tumble.md`), so `TumblePlugin` works with no extra install. The backend-neutral `Physics` singleton rides the main barrel too: game code reads `Physics.backend` (`readBody` / `gravity` / `setKinematic`), so the swap-facing read surface belongs beside `Tumble`, while `installBackend` / `uninstallBackend` + the `StepSystem` / `ConstraintSystem` / `ComposeSystem` anchors stay on `physics/core` (the backend-implementer surface). `AvbdPlugin` sits behind the **`./avbd` subpath** so a tumble-default app never even names it. Neither backend module has an import-time side effect, so a physics-free app tree-shakes both away (physics stays zero-cost by default, the viz-engine floor).

## Registry pattern

`Registry<T>` (`engine/utils/registry.ts`, on the barrel) — name-keyed, auto-assigns a stable numeric ID. `.register(spec)` returns the ID; `.delete(name)`, `.clear()` (the reload seam — wipes all entries + the ID space for a clean rebuild), `.get(name)`, `.id(name)`, `.name(id)`, iteration via `Symbol.iterator`. The renderer uses it for `Surfaces` / `Draws` / `Meshes`; producers call `.register(...)` directly.

`mesh()` wraps `Meshes.register(...)` because it does real work first (allocates GPU buffers from typed arrays). Plain pass-through wrappers don't exist — `.register()` / `.delete()` convey the intent.

## Type discipline

- No type aliases that just rename primitives (`type Foo = string`). Use the primitive directly.
- Interfaces earn their place by having >1 field or methods.
- Don't export types used only within one file.

## Naming

Exports should not commonly conflict (no `as` renames at import sites). If a name is too generic (e.g. `readBuffer`), it belongs in a subpath or stays internal — not the main barrel. (anti-pattern)
