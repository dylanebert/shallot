# Shallot project

Explore this project's entry, plugins and checks first; reuse its setup.

- Learn the API from the installed package, not memory. `bunx shallot create --help` lists the examples in `node_modules/@dylanebert/shallot/examples/`; start from the nearest one, its implementation and its checks, then the JSDoc in `node_modules/@dylanebert/shallot/src/` for the APIs it uses.
- Check your work as that example's checks do, with the cheapest evidence that answers: state, then a captured frame, then the browser.
- While you iterate, run only the check that answers your change: `bun test ./<file>` or `bunx playwright test <file>`. Before you finish, run `bun test` once; CI, `.github/workflows/test.yml`, runs every tier.
- `bun test` runs `*.test.ts` and `*.gpu.test.ts` only; run a `*.node.ts` check by path with `bun test ./<file>`. A full renderer or physics composition is a `tests/<goal>.node.ts` check, not a `*.gpu.test.ts`.
- `bunx shallot publish` builds, publishes to Cloudflare, or to itch.io with `--target itch`, and verifies the public game; read `bunx shallot publish --help` first. Commit its `package.json` destination and dependency changes. A first-link name collision refuses rather than overwrites; do not write `shallot.publish` by hand unless updating that Worker is explicitly intended. An itch.io page is created and set up by a person on itch.io; publish names the settings it cannot verify.
- Cleanup stays the provider's; Shallot has no unpublish or list command. Read `shallot.publish` in `package.json`: below, `<account>` is `accountId`, `<name>` is the Cloudflare `name`, and `<user>/<game>` is the itch.io `name`. Run the project's pinned `bunx wrangler` from the project; use the quoted cached butler path printed by publish as `<butler>`.
- Cloudflare owns login (`CLOUDFLARE_ACCOUNT_ID=<account> bunx wrangler login`, add `--device` remotely), preview (`CLOUDFLARE_ACCOUNT_ID=<account> bunx wrangler dev --assets <web-build-directory>`), “roll back” (`CLOUDFLARE_ACCOUNT_ID=<account> bunx wrangler rollback --name <name>`), and “take the game down” (`CLOUDFLARE_ACCOUNT_ID=<account> bunx wrangler delete --name <name>`). “See what is published”: `https://dash.cloudflare.com/<account>/workers/overview` lists every Worker in the account; Wrangler has no account-wide list command.
- itch.io owns login (`"<butler>" login`), builds (“see what is published”: `"<butler>" status <user>/<game>`), and pages (`https://itch.io/dashboard`, choose the game's Edit page). Preview locally with `bun run preview`; “roll back”: check out an earlier commit, `bun run build`, then `"<butler>" push <web-build-directory> <user>/<game>:html5`. “Take the game down”: set Visibility to Draft on its Edit page; butler cannot unpublish or delete pages.
- Confirm with the person before deleting a Worker or taking a page down. Wrangler delete auto-confirms without a TTY or in CI; it will not ask an agent, and deletion cannot be undone. More detail: `bunx shallot publish --help`.
- Publishing without interaction needs the provider's credentials (`CLOUDFLARE_API_TOKEN`, plus `CLOUDFLARE_ACCOUNT_ID` when ambiguous; butler's stored credentials or `BUTLER_API_KEY` for itch.io). CI's least Cloudflare token is custom, with Account → Workers Scripts → Edit on the one account; the "Edit Cloudflare Workers" template is broader. butler's login key has `wharf` scope, managing builds on every project the identity can reach, not one game; an account-settings API key can be broader still. Never put credentials in `package.json`. Publish adds no credentials to the build; Vite's client values, public files and source maps can still disclose what the project puts there. Never put secrets in them.
