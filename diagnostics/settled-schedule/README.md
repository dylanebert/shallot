# Settled schedule measurement

This is the stage-1 browser oracle for `units/settled-schedule.md`. It measures the accepted premise, not an engine behavior change. Run the committed revision in headed Chrome on each named display. The Chrome process must use a fresh temporary profile; do not alter the user's browser or display settings. The Omarchy run must use a scratch tree made from this commit with `git archive`, never `~/kex/shallot`.

## Fixed reading rule

For each 30-second run, start the clock at the first rAF timestamp. For every callback whose timestamp is less than 30,000 ms after that first timestamp, retain the rAF timestamp, the interval from the preceding callback (null for the first), and `world.gpu.pending()` sampled at callback entry before stepping. Also retain the adapter identity/features and browser/display dimensions. On the first callback at or after 30 seconds, preserve a separate `closingCallback` with its timestamp, interval and pending count, then stop. The closing interval is reported separately and excluded from the 30-second interval distribution and double-fire count; it makes a long gap at the end visible. Preserve the callback rows in the browser result object; the collector can export that object as JSON.

Summarize rAF intervals using min, nearest-rank p50/p90/p95/p99, and max. Pending trend is the sequence of each elapsed one-second bucket's maximum, plus the least-squares slope of those bucket maxima in frames/second. Report the overall maximum and the first-to-last bucket maxima as well. Call pending bounded only if it has no sustained upward trend and does not reach the safety stop. The GPU-bound run stops immediately if pending reaches 64, or if five successive one-second bucket maxima are strictly increasing by at least one frame each and span at least eight frames; preserve the partial record and do not continue to another run on either host. This is a safety stop, not a claim that any finite sample proves mathematical boundedness.

Count a double-fire only after 20 prior positive rAF intervals exist: the current interval is a double-fire when it is strictly less than half the median of those preceding 20 intervals. The current interval is not included in its own threshold. Count only callbacks in the 30-second window. Use this exact rule for the loading-screen run.

The GPU-bound composition requests `timestamp-query` and records GPU timestamps around its per-frame compute dispatch for the first 32 frames. Its dispatch uses the full device-supported workgroup dimension and a URL-selected number of dependent iterations per invocation. Use `?iterations=500` on the Mac and `?iterations=15000` on Omarchy; retain the selected count in the result. The run is valid only if the dispatch's minimum measured GPU duration exceeds the host display period (1 / measured refresh); report the 32-sample min/median/max against that period. The scene also renders the loading-screen WebGPU canvas. If the timestamp feature is unavailable or the minimum does not exceed the period, report that the GPU-bound check was not established; do not label it a passing run.

## Run procedure

1. Commit this rule and the diagnostic scene/collector before each 30-second measurement. Keep the engine code fixed across hosts; record the exact commit and URL-selected workload used for each run. If a calibration fails the GPU-duration premise, commit the revised workload rule before repeating.
2. Make the local-only `src/engine/app/index.ts` run patch: remove the two early returns for `coalesce(...)` and `pending() >= MAX_FRAMES_IN_FLIGHT`, but leave the rest of the loop unchanged. After computing `t` and updating `lastCallback`, sample `const pendingCount = pending?.() ?? 0`, call `(globalThis as typeof globalThis & { __shallotScheduleFrame?: (timestamp: number, pending: number) => boolean }).__shallotScheduleFrame?.(t, pendingCount)` on every callback, and if it returns `true`, call `world.dispose()` and return from that callback. Do not commit this patch. Apply the same local diff in the Omarchy archive scratch tree only.
3. Install the archived tree's dependencies. Serve the GPU scene with `bun node_modules/vite/bin/vite.js --config diagnostics/settled-schedule/vite.config.ts` (port 4173). Serve the loading-screen example separately with `bun node_modules/vite/bin/vite.js --config diagnostics/settled-schedule/vite.loading-screen.config.ts` (port 4174); its absolute `/src/...` URLs require the example as Vite's root. Launch headed Chrome with a temporary `--user-data-dir`, a free `--remote-debugging-port`, and `--start-fullscreen` for both cases; these flags leave the user's profile untouched. Open `/diagnostics/settled-schedule/?iterations=500` on the Mac and `/diagnostics/settled-schedule/?iterations=15000` on Omarchy for the GPU scene. For double-fire navigate to `http://127.0.0.1:4174/?schedule=double-fire`; locally import `installScheduleRecorder` from `../../../diagnostics/settled-schedule/recorder` in `examples/loading-screen/src/main.ts` and call it for that query before `runApp`. For that run only, apply a local CSS override that hides `.description`, makes `.page` full-size with no padding, and sets `.frame { width: 100vw; height: 100vh; aspect-ratio: auto; }`. These temporary app/CSS edits are not committed.
4. Capture the display's current mode/refresh (`CGDisplayCopyDisplayMode` on macOS; `hyprctl monitors all` on Omarchy) and the browser result's adapter identity before analyzing. Run the GPU scene first. If its pending safety stop fires on either host, stop the stage there and do not run the double-fire case. Otherwise run the loading-screen case in Chrome fullscreen at the display's highest already-available/current mode; do not change the display mode.
5. Use `bun diagnostics/settled-schedule/collect.ts /diagnostics/settled-schedule/` or `bun diagnostics/settled-schedule/collect.ts schedule=double-fire` while the page is open to print the stored result object. Save that output outside the source tree. The page keeps all callback rows in `window.__shallotScheduleResult` and shows the run state in a small overlay. Compare the GPU timestamps with the display period and summarize both callback streams by the rules above.

The source revision's commit message records the machine, adapter, current/highest refresh, pending maximum and trend, rAF interval distribution, timestamp evidence and double-fire count for each completed host/run. Raw callback rows are collected for audit but are not checked into the tree.
