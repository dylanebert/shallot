## Reading the split

Each phase has (a) serial TS, (b) kernel work, (c) threading below. Sampled TS/kernel/join are absolute main-thread ms/step, not additive allocations of the median native gap: native includes corresponding serial work and independently taken medians do not add. Inclusive callees overlap their parents. Kernel samples include internal WASM stage waits; JS join measures only pool acknowledgement after the caller's kernel task returns. Worker wake latency and internal stage barriers are not separately measured. Their narrowest measured bound is the kernel envelope, not an invented platform surcharge. A zero sample means below this window's sampling resolution, not zero cost.

Shallot constraints contains kernel finalization; transforms measures its serial tail. Native transforms measures parallel finalization, and native refit separately measures its serial tree tail. Compare whole solve for an aligned envelope; do not subtract transforms as though the phase definitions matched. Shallot's solverSetup/prepareConstraints/integrateVelocities/warmStart/solveImpulses/integratePositions/relaxImpulses/applyRestitution/storeImpulses/refit counters are uninstrumented zeros, NOT avoided work. A finer split would require kernel timing instrumentation; no product change is authorized here. Narrowest remaining solve-kernel point is runMt's solve stage. splitIslands, sensorHits, jointEvents, hitEvents, bullets, sleepIslands and sensors round to 0.00 in these windows on both sides. Their three parts are unresolved below reporting precision, kept as no demonstrated material gap in these scenes (not a promise for scenes using those features).

## Cross-cutting open items

**Stage 8 one-thread pairs:** do not relabel its unresolved +1 ms as closed. Fresh `git archive 1ed733ec` (pre-stage-8), symlinked dependencies, bundled scenes, no CPU profiler; interleave B A B A at junkyard 1 thread, 200 steps, last ten steps 190–199. Pair medians [five-step halves]: B1 11.544 [11.499,11.588], A1 current 11.098 [10.361,11.156]; B2 10.306 [10.033,10.452], A2 10.246 [10.123,10.342]. A−B −.445/−.060 ms; A1 halves drift ~7.7%, B2 ~4.2%; these are load bounds, not a clean stage-8-only attribution (later stages alter cache/memory state). No consistent current one-thread slowdown is demonstrated. Narrowest known new work remains atomic candidate allocation/list writes/merge, previously bounded by reviewer at ~2,000 candidates: attributing +1 ms wholly to it would be ~500 ns/candidate, not a measured cost. **Closable investigation:** query-only interleaved counts/timing before removing any deterministic list work; **kept** unresolved historical observation, not dismissed as noise.

**Custom callbacks:** all three benchmarks use defaults; custom path contributes zero to these measured gaps, no custom-callback latency estimate. Pair custom filtering and material callbacks still execute serial JS; material callback path additionally reads poses/materials and handles compound/mesh mapping in finish. **Kept:** synchronous arbitrary JS cannot execute in a WASM worker as native C callbacks do. **Closable:** keep default branches fully kernel-owned; offer kernel-expressible policies only if a user need justifies them. Jolt build itself warns multithreading is incompatible with JS callbacks [W2]; box2d3-wasm's maintainer reports `val accessed from wrong thread` and a deadlock when trying proxying [W4]. This is a reported limitation, not proof the issue remains unresolved today. No claim that proxying solves Shallot's callback semantics.

**Whole step:** sums of phase medians need not equal step median. Unassigned remainder is bounded by setup/reserve/body staging/event-buffer housekeeping and measurement differences; no additional material kernel or thread phase was found. Keep lightweight TS coordination; investigate only a counted residual. The unit has no speed gate.
